# Residual review findings — U4–U7 (head 4e55e42)

Source: 5-reviewer `ce-code-review` (security / correctness / reliability / api-contract / testing) of the Top-Level Todos & GitHub Issues Sync feature (base `13dfd2f`, head `4e55e42`). The significant findings were applied in commit `4e55e42`; the items below are P3 / advisory / test-quality and remain open. None are merge-blocking.

## Correctness / reliability (P2–P3)

- **Deletion-detection cost on change-syncs (P2, partially addressed).** Gating on `notModified` (304) fixed the common-case budget drain, but on a non-304 sync the loop still calls `adapter.getIssue` once per github-origin todo not present in the changed set. For a repo with many linked issues this is N calls per change-sync. Complete fix: a throttled "deletion sweep" (one paginated `listIssues(state=all)` per repo, time-gated, e.g. hourly) whose number set is diffed against linked todos.
- **`origin_deleted` can stick on restore (P3).** The deletion-detection loop skips todos already marked `originDeleted`; if GitHub restores an issue without bumping `updated_at`, the flag is never cleared. Mitigation: periodically re-verify `originDeleted` todos, or clear optimistically when the issue reappears in any form.
- **`markTodoCommentPushed` failure after a successful `addComment` (P3).** If the SQLite write throws after the remote comment is created, the local comment stays `pushed=0` with no `remote_id` and the next sync creates a duplicate GitHub comment. Mitigation: persist `remote_id` before anything else; on retry, match by body+author+window.
- **`publish()` has no single-flight (P3).** Concurrent publishes of the same todoId both pass the not-linked guard and create two remote issues; the second overwrites the row, orphaning the first issue on GitHub. Mitigation: a per-todo mutex or a DB "publishing" flag.
- **`SyncResult.conflicts` counter inflates for unresolved conflicts (P3).** Each sync re-detects an unresolved title conflict and increments the metric; the conflict *record* is idempotent (only the reported count drifts). Compute the count from outstanding conflict rows at the end of reconcile instead.

## API / UX (advisory — matches current client behavior)

- `GET /api/github/repos` returns `400` for not-connected; `401` would be more semantically correct and lets a client interceptor steer to reconnect. `requireAdapter()` throws the same `400`.
- `POST /api/github/device-flow/start` returns a bare object, not a named envelope (every other route wraps in `{ connection }` / `{ repos }` etc.). The client matches the bare shape; changing it is a coordinated server+client change.
- No `POST /api/github/device-flow/cancel` endpoint — an orphaned in-flight device flow (user closes the modal mid-flow) is cleared only on the next `startDeviceFlow` or `shutdown()`.
- PAT disconnect does not server-side revoke (the plan's R18 specifies a manual deep link for PATs). Future enhancement: token-self-revocation (`DELETE /applications/{client_id}/token` with the token as Bearer) before surfacing the manual link.

## Test quality (P3)

- The device-flow terminal-state test ("expired / access_denied") only exercises `expired_token`; the `access_denied` and `incorrect_device_code` cleanup branches are not covered (split into independent tests).
- The sync-engine fake's `getIssue` returns a phantom default issue for unknown numbers instead of `null`; it works around this via `deletedNumbers`. Making it return `null` for unstored numbers would match the real adapter's 404→null contract and be less fragile.
- The "304 short-circuit" test covers engine-level empty-list handling, not the octokit adapter's actual 304→empty conversion (no test instantiates `createOctokitAdapter` against a mocked HTTP layer). Rename for clarity, or add an adapter-level 304 test.
