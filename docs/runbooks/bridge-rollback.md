# Bridge release rehearsal & rollback runbook (U6 / KTD-3 / KTD-8 / KTD-9)

Audience: whoever cuts the **first Electron release** (the bridge release) and
every release after it until the Tauri install base reaches zero.

The bridge release is a single GitHub release carrying **two manifest
families**:

- `latest.json` (tauri format) — serves the last Tauri clients (0.0.33).
  Generated by `scripts/build-bridge-manifest.ts`; its URLs point at the
  Electron installers.
- `latest.yml` / `latest-mac.yml` (+ blockmaps) — serve the Electron line
  (electron-updater, U5).

**Hard gate: the two-OS rehearsal below must pass before the bridge release
is published.** A failed rehearsal means STOP and fall back to a custom Tauri
bridge build (plan U6 Stop conditions / Risks: "Windows bridge payload
execution unproven").

## 0. Preconditions

- CI green on the release tag, including the `bridge-manifest` job (which
  fails the build when `latest.json` is missing or any platform signature
  does not verify against the released bytes — KTD-3 guard).
- Draft release `vX.Y.Z` exists with all assets: `Comate-X.Y.Z-mac-{arm64,x64}.app.tar.gz`,
  `Comate-X.Y.Z-win-x64.exe`, dmg/zip, `latest*.yml`, blockmaps, `latest.json`,
  and the `.sig` files.
- `X.Y.Z > 0.0.33` (enforced by the generator and by CI check).
- Test machines: one macOS (arm64; x64 optional) and one Windows 10/11 x64,
  each with the **last Tauri build (0.0.33) really installed** and used (a
  workspace + session data + at least one remembered site login).

Local dry-run of the manifest machinery (no release needed):

```bash
tsx scripts/build-bridge-manifest.ts generate --version 0.1.0 --tag v0.1.0 \
  --asset darwin-aarch64=Comate-0.1.0-mac-arm64.app.tar.gz=@path/to.sig \
  --asset darwin-x86_64=Comate-0.1.0-mac-x64.app.tar.gz=@path/to.sig \
  --asset windows-x86_64=Comate-0.1.0-win-x64.exe=@path/to.sig --out latest.json
tsx scripts/build-bridge-manifest.ts check latest.json --assets-dir <dir-with-the-3-assets>
```

`check --assets-dir` cryptographically verifies each platform signature
against the downloaded asset bytes — this is the step that errors when
minisign ran **before** Authenticode/notarize (KTD-9 order inversion).

## 1. Rehearsal matrix (the hard gate)

Draft-first: while the release is still a draft, download assets via the
GitHub API (drafts are invisible to `/releases/latest/download/*`). To make
the Tauri client see the draft manifest, either publish-then-rehearse on a
throwaway tag, or temporarily host the draft's `latest.json` at a test URL
and point a test build of the old client at it. Record which route was used.

### 1a. macOS (arm64) — from the last Tauri install

- [ ] Install Tauri Comate 0.0.33, create a workspace, run one session,
  log in to one site in the embedded browser (remember-site).
- [ ] Trigger update check in the old client → it offers X.Y.Z from
  `latest.json` (platform key `darwin-aarch64`).
- [ ] Download verifies (minisign) and installs; app relaunches as the
  Electron build.
- [ ] **Data assertion:** `~/Library/Application Support/com.comate.app`
  contents carried over — workspace list, sessions, SQLite intact (KTD-7).
- [ ] **Login assertion:** the remembered site re-authenticates via the
  site-auth store (CfT profile cookies are NOT migrated — AE1 semantics).
- [ ] New-line self-update: from the Electron build, update once more via
  `latest-mac.yml` to a subsequent build (or re-serve the same version as
  X.Y.Z+1) → electron-updater path works end to end.
- [ ] Repeat on x64 (`darwin-x86_64`) if an Intel machine is available;
  otherwise record as covered-by-key-symmetry.

### 1b. Windows (x64) — from the last Tauri install (MSI)

- [ ] Install Tauri Comate 0.0.33 MSI (per-machine), create data + site
  login as above.
- [ ] Trigger update check → offers X.Y.Z (platform key `windows-x86_64`).
- [ ] Old client downloads `Comate-X.Y.Z-win-x64.exe`, verifies the
  minisign signature, and executes it. **Known payload caveat (Risk,
  plan line ~250):** the old client launches the NSIS exe with
  `/P /UPDATE /R /ARGS ...` (tauri default install mode `Passive`);
  electron-builder's NSIS ignores those flags and shows its normal
  oneClick UI. Confirm the installer proceeds to completion from this
  invocation — this is the single most unproven step of the bridge.
- [ ] During install, the legacy-MSI cleanup (`build/nsis-include.nsh`)
  detects the 0.0.33 per-machine MSI and runs `msiexec /x` **with UI**;
  accept the single UAC prompt → old install removed.
- [ ] **Data assertion:** `%APPDATA%\com.comate.app` carried over.
- [ ] **Login assertion:** site re-auth via site-auth store (AE1).
- [ ] **No dual-install residue:** only one Comate in Apps & Features
  (the per-user NSIS one); old all-users Start Menu/Desktop shortcuts gone;
  `C:\Program Files\Comate` removed by msiexec.
- [ ] New-line self-update via `latest.yml` once more → works.
- [ ] **UAC-refusal branch:** repeat the install on a second machine (or
  VM snapshot) and DECLINE the UAC prompt at the msiexec step → installer
  continues, shows the one-time cleanup notice; old shortcuts are removed
  on a best-effort basis (the per-user installer is unelevated, so deletion
  from the all-users profile may be denied — tolerated residue per KTD-8);
  the old app files remain but the new app works. A manual
  "Settings > Apps > Comate (old)" uninstall afterwards completes cleanup.

### 1c. Linux

Clean-install smoke only — covered by `linux-smoke.md` (no Tauri Linux
install base to bridge: the old line shipped macOS+Windows only).

### 1d. Dual-family serving (integration)

- [ ] With the release published: `GET /releases/latest/download/latest.json`
  returns the tauri manifest pointing at Electron assets (old line), and
  `latest.yml` / `latest-mac.yml` / `latest-linux.yml` resolve for the new
  line — both families served from the same release.

## 2. Rollback

If the bridge release misbehaves after publication:

1. **Do not delete the release.** Deleting breaks both updater families for
   everyone who already fetched a manifest.
2. Old-line clients that already updated are on the Electron line and follow
   `latest*.yml` — ship a fix as a normal Electron patch release.
3. Old-line clients that have NOT updated still see `latest.json`. If the
   bridge update itself is harmful (e.g. data loss on migration), replace
   `latest.json` on the release with one whose `version` is `0.0.33`
   (or delete just the `latest.json` asset) so remaining Tauri clients stop
   offering the update — regenerate with
   `tsx scripts/build-bridge-manifest.ts generate --version 0.0.33 ...`
   using `--pub-date` of the original and re-upload (the version floor is a
   generator guard; bypass only for this rollback scenario by checking out
   the script and editing the floor, or by hand-editing the JSON).
4. The last Tauri installer (0.0.33) remains available from the v0.0.33
   release for manual reinstall; user data in `com.comate.app` dirs is
   untouched by rollback (KTD-7: both lines share the data dir).

## 3. Asset retention obligation (KTD-3)

From the bridge release onward, **every release must carry `latest.json`**
(pointing at that release's Electron installers) until telemetry confirms
the Tauri install base has reached zero. CI enforces this: the
`bridge-manifest` job fails the build when `latest.json` is absent or its
signatures don't verify. When the base is confirmed zero, remove the
`bridge-manifest` job, this runbook's rehearsal section, and
`scripts/build-bridge-manifest.ts` in one cleanup PR.

Never delete bridge assets (`*.app.tar.gz`, NSIS exe, `.sig`, `latest.json`)
from any release that Tauri clients may still point at.

## 4. Rehearsal failure fallback

Any rehearsal failure on the matrix above → STOP the release. Fallback per
plan U6 Stop conditions: build a **custom Tauri bridge release** (a final
Tauri build whose updater payload/install logic performs the handoff)
instead of serving Electron installers through the stock updater path.
Escalate to the migration owner; do not patch around a failed rehearsal by
publishing anyway.
